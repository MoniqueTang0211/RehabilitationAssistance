# 老年康复辅助平台 · 三人分工明细与协作规范

> 依据《老年康复辅助平台-老人端-轻量架构设计.md》制定。
> 分工原则：**页面纵向切片** —— 每人负责自己页面的「前端页面 + 对应后端模块」全链路，避免联调互相等待。

## 一、成员分工总表

| 成员 | 角色 | 前端页面 | 后端模块 | 公共职责 |
| --- | --- | --- | --- | --- |
| **A** | 底座负责人 | Login、Home（康复进度） | auth、user、progress、common（中间件） | 项目底座搭建、统一响应/错误码、适老化样式变量、分支与 PR 规范维护 |
| **B** | 训练模块负责人 | Training（今日任务 + 打卡 + 图文指引） | task、plan | 公共组件：TaskCard、ProgressBar |
| **C** | 关怀与设置负责人 | Mental（每日金句）、Message（求助留言）、Profile（字体设置） | quote、message | 公共组件：QuoteCard、MessageForm、FontSizeSetting；拨号封装 dial.js |

### 工作量说明

- A 的底座工作（目录、请求层、中间件、配置）与 B/C 的单个页面体量相当，整体均衡。
- C 负责三个页面，但 Mental 页面极轻（一个卡片），Profile 仅字体三档调节，实际工作量与 A/B 持平。

## 二、页面 ↔ 接口 ↔ 数据文件 对照表

| 成员 | 页面 | 消费接口（已定于设计文档 4.2） | 读写数据文件 |
| --- | --- | --- | --- |
| A | Login | `POST /api/auth/login` | `user.json` |
| A | Home | `GET /api/progress` | `progress.json` |
| A | — | `GET /api/user/profile`、`PUT /api/user/settings`（供 Profile 调用，A 实现） | `user.json` |
| B | Training | `GET /api/tasks`、`GET /api/tasks/:id`、`GET /api/plans/today`、`POST /api/plans/checkin`、`GET /api/plans/records` | `tasks.json`、`dailyPlan.json` |
| C | Mental | `GET /api/quotes/today` | `quote.json` |
| C | Message | `GET /api/phrases`、`POST /api/messages` | `quickPhrase.json`、`message.json` |
| C | Profile | 复用 A 的 `/api/user/profile`、`/api/user/settings` | — |

> 初始数据（训练项目、快捷语句、金句）：B 负责 `tasks.json`，C 负责 `quickPhrase.json` 与 `quote.json`，A 负责 `user.json` 种子账号（含 bcryptjs 哈希密码）。

## 三、Git 分支与 PR 规范

### 3.1 分支模型

```
main          ← 只放可运行版本，禁止直接 push，只能 PR 合入
└─ dev        ← 日常集成分支，功能完成后 PR 进 dev
   ├─ feat/login-home        （A：底座 + 登录 + 首页进度）
   ├─ feat/training          （B：训练与打卡）
   └─ feat/mental-message-profile （C：金句 + 留言 + 设置）
```

### 3.2 提交与 PR 规则

| 规则 | 说明 |
| --- | --- |
| 提交信息 | `feat/fix/docs: 一句话说明`，如 `feat: 完成今日任务列表展示` |
| PR 要求 | 必须 1 人 review 后才能合入；合入 dev 前需本地跑通双方模块 |
| 公共文件 | `router/index.js`、`styles/*.css`、`api/request.js`、`store/index.js`、所有中间件归 A 维护，B/C 修改需 A review |
| 领取页面 | 各自页面目录 `views/`、自己的 `api/*.js`、自己的 `routes/*.route.js` 等，他人不得修改 |

### 3.3 冲突高风险点与对策

| 高风险文件 | 对策 |
| --- | --- |
| `client/src/router/index.js` | A 在底座阶段建好全部 5 条路由与占位页面，B/C 只改自己页面文件，不动 router |
| `server/data/*.json` | 运行期会被写入。**提交前恢复为初始内容**（或各自只在本地改，初始数据单独提交一次） |
| `styles/variables.css` | 字号三档变量由 A 一次定稿，其他人只消费变量不新增变量 |

## 四、里程碑建议（按依赖顺序）

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| M1 底座 | A 搭完前后端骨架、统一响应、路由占位，push 到 dev | 无 |
| M2 登录打通 | A 完成 auth 全链路；B/C 用假 token 先开发页面布局 | M1 |
| M3 各自模块 | B 完成 task+plan；C 完成 quote+message；A 完成 progress+user | M2 |
| M4 联调验收 | 三人在 dev 上集成、互相 review、真机局域网验证 | M3 |

## 五、开发约定速查（全员必须遵守）

1. 页面禁止直接写 axios，统一走 `src/api/`；接口函数一个模块一个文件。
2. 后端依赖方向 `routes → services → repositories → models`，禁止跨层直调。
3. 响应统一 `{ code, message, data }`，错误码见设计文档 5.1，禁止各自造格式。
4. 业务代码禁止硬编码端口、密钥、地址，一律走 `src/config`。
5. 前端渲染用户输入只用文本插值，禁止 `v-html`。
6. 日志不含密码与 token 全文。
